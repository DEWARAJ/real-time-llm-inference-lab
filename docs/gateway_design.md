# SLO-Aware Inference Gateway

The gateway adds a production-serving layer in front of any OpenAI-compatible vLLM or SGLang backend. Its purpose is to preserve interactive latency during overload instead of accepting unlimited work and failing unpredictably.

## Request path

1. Estimate prompt and output token demand.
2. Predict completion time from queue demand and an EWMA service rate.
3. Reject work that exceeds request-count, token-capacity, or deadline limits.
4. Select a token-budgeted dispatch batch using FIFO, shortest-first, priority, or prefix-aware scheduling.
5. Forward the request to the model backend and expose TTFT, queue, completion, failure, and rejection metrics.
6. Open a circuit after repeated backend failures and probe recovery after a cooldown.

## Headers

- `x-llm-deadline-ms`: end-to-end latency target used by admission control.
- `x-llm-priority`: integer request priority; larger values dispatch first under the priority policy.

## Evidence boundaries

`results/gateway_simulation.json` is generated by a deterministic queueing simulation. It tests policy invariants and overload behavior but is not presented as a GPU measurement. Live GPU results must be collected separately by running the gateway in front of the included vLLM configuration and using the HTTP benchmark harness.

## Deployment

The Docker image contains only the gateway. The Kubernetes manifest expects an OpenAI-compatible backend at `http://vllm:8000`. Health probes, resource boundaries, a service, and a CPU-based HPA are included. Production deployment should add authentication, TLS, distributed queue state, backend discovery, and a queue-depth custom metric for autoscaling.
